# NASA ICD PDF Conversion and Regeneration Pipeline

## 1. Project Objective

Build a reliable pipeline that converts NASA Interface Control Document PDFs into an editable, version-controlled intermediate representation that can:

* Preserve original document content.
* Preserve page-level source traceability.
* Represent requirements, interfaces, tables, diagrams, signals, messages, and metadata.
* Regenerate updated PDFs and other document formats.
* Support controlled edits without manually rebuilding the document.
* Validate both engineering meaning and visual fidelity.
* Identify differences between the original and regenerated document.
* Support future search, retrieval, comparison, and automated analysis.

The pipeline must not treat PDF as the authoritative editable format.

The authoritative source will be a structured intermediate representation stored in version control.

---

# 2. Core Design Principle

The conversion architecture will follow this model:

```text
Original PDF
    ↓
PDF and page classification
    ↓
Text, geometry, table, image, and vector extraction
    ↓
Layout-aware document representation
    ↓
Semantic ICD representation
    ↓
Human validation and correction
    ↓
Version-controlled canonical source
    ↓
Deterministic generation
    ↓
PDF, HTML, DOCX, SVG, and searchable representations
    ↓
Semantic and visual regression testing
```

The system will use separate representations for:

1. The physical layout of the original document.
2. The engineering meaning contained in the document.

---

# 3. Functional Requirements

## 3.1 PDF Ingestion

The system shall:

* Accept digitally generated PDFs.
* Accept scanned PDFs.
* Accept PDFs containing mixed digital and scanned pages.
* Calculate and store a SHA-256 hash for every source document.
* Record the original filename, page count, dimensions, and metadata.
* Determine whether each page contains:

  * Native text.
  * Raster images.
  * Vector graphics.
  * Tables.
  * Diagrams.
  * Scanned content.
* Detect page rotation.
* Detect unusual page sizes and foldout-style pages.
* Preserve the original PDF as an immutable source artifact.

---

## 3.2 Page Classification

Each page shall be classified as one or more of the following:

* Native digital text page.
* Scanned page.
* Mixed-content page.
* Table-heavy page.
* Diagram-heavy page.
* Drawing-heavy page.
* Image-only page.
* Cover page.
* Revision-history page.
* Table-of-contents page.
* Requirements page.
* Appendix page.

Example:

```yaml
pages:
  - page_number: 17
    classification:
      - scanned
      - table_heavy
    native_text_available: false
    ocr_required: true
    rotation_degrees: 0
    confidence: 0.98
```

---

## 3.3 Text Extraction

The system shall:

* Prefer native PDF text extraction over OCR.
* Extract individual words and text blocks.
* Preserve:

  * Page number.
  * Bounding box.
  * Reading order.
  * Font name when available.
  * Font size.
  * Font emphasis.
  * Text colour when relevant.
* Identify headings and hierarchy.
* Detect repeated headers and footers.
* Detect captions.
* Detect page numbers.
* Detect section numbering.
* Preserve text verbatim before normalization.

Example:

```yaml
id: block-p12-b07
type: paragraph
page: 12
bbox:
  x0: 72.4
  y0: 188.2
  x1: 522.1
  y1: 244.8
text_verbatim: >
  The C&DH subsystem shall transmit...
reading_order: 19
style:
  font_name: Helvetica
  font_size_pt: 10
  bold: false
confidence: 0.97
```

---

## 3.4 OCR

OCR shall be used only when:

* Native text is unavailable.
* Native text is corrupted.
* Text is embedded in an image.
* Diagram labels cannot be extracted directly.
* Scanned tables require recognition.

OCR processing shall:

* Preserve character-level or word-level confidence where available.
* Retain the original image region.
* Mark OCR-derived text separately from native text.
* Avoid silently replacing uncertain values.
* Flag low-confidence content for review.
* Support manual correction.

---

## 3.5 Requirement Recognition

The system shall detect candidate requirements using:

* Requirement identifiers.
* Section numbering.
* Normative terms such as:

  * Shall.
  * Must.
  * Will.
  * Should.
* Verification matrices.
* Requirement allocation tables.
* Cross-references.
* Requirement-specific formatting.
* Interface identifiers.
* Terms including:

  * TBD.
  * TBR.
  * TBC.
  * TBS.

Each requirement shall contain:

```yaml
requirements:
  - id: REQ-CMD-001
    text_verbatim: >
      The flight computer shall accept command transfer frames.
    text_normalized: >
      The flight computer shall accept command transfer frames.
    requirement_type: interface_requirement
    verification_method: test
    section: "3.2.4"
    source:
      page: 12
      block_id: block-p12-b07
      bbox: [72.4, 188.2, 522.1, 244.8]
    extraction_confidence: 0.97
    human_verified: false
```

The system shall never rewrite normative requirement language without a recorded human-approved change.

---

## 3.6 Table Extraction

The system shall:

* Detect ruled and unruled tables.
* Preserve row and column structure.
* Detect:

  * Merged cells.
  * Row spans.
  * Column spans.
  * Multi-line cells.
  * Repeated table headers.
  * Footnotes.
  * Units.
* Preserve original table geometry.
* Preserve the logical table structure separately from the layout.
* Record extraction confidence at table, row, and cell level.
* Allow manual correction.

Example:

```yaml
tables:
  - id: TBL-4-7
    caption: Command Packet Definition
    source:
      page: 26
      bbox: [48, 177, 560, 698]

    columns:
      - id: field
        title: Field
      - id: bits
        title: Bits
      - id: description
        title: Description

    rows:
      - id: row-001
        cells:
          field:
            value: Version
          bits:
            value: 3
          description:
            value: Protocol version identifier
```

---

## 3.7 Diagram Recognition

The system shall distinguish between:

* Architecture diagrams.
* Interface block diagrams.
* Sequence diagrams.
* State diagrams.
* Data-flow diagrams.
* Timing diagrams.
* Charts.
* Wiring drawings.
* Technical illustrations.
* Screenshots.
* Raster figures.

Semantic diagrams shall be converted into an editable graph representation.

Example:

```yaml
diagrams:
  - id: DIA-IF-003
    type: interface_block

    nodes:
      - id: spacecraft
        label: Spacecraft
        node_type: system
        position:
          x: 120
          y: 180

      - id: ground
        label: Ground Segment
        node_type: system
        position:
          x: 460
          y: 180

    edges:
      - id: edge-001
        from: ground
        to: spacecraft
        label: Command Uplink
        interface_reference: IF-CMD-001
```

The system shall preserve the original figure as a reference image even when an editable diagram is generated.

# 4. Intermediate Representation

## 4.1 Two-Layer Representation

The project shall maintain two linked intermediate representations.

### Document Intermediate Representation

The Document IR represents the physical document.

It shall include:

* Pages.
* Page dimensions.
* Blocks.
* Coordinates.
* Fonts.
* Paragraphs.
* Lines.
* Shapes.
* Tables.
* Images.
* Captions.
* Headers.
* Footers.
* Reading order.
* Layout relationships.
* Source provenance.

### Semantic ICD Intermediate Representation

The ICD IR represents engineering meaning.

It shall include:

* Requirements.
* Interfaces.
* Messages.
* Signals.
* Systems.
* Protocols.
* Units.
* Field definitions.
* Verification information.
* Relationships.
* Cross-references.
* Revision metadata.

The two models shall be linked through stable identifiers.

# 5. Provenance Requirements

Every extracted element shall retain provenance.

Example:

```yaml
provenance:
  source_document: NASA-ICD-001-REV-C.pdf
  source_sha256: sha256-value
  page: 31
  bbox:
    x0: 74.2
    y0: 211.5
    x1: 521.8
    y1: 243.1
  extraction_engine: docling
  extraction_engine_version: 2.x
  extraction_confidence: 0.94
  extraction_timestamp: "2026-07-25T12:00:00Z"
  reviewer: null
  human_verified: false
```

Provenance shall support:

* Source-to-output traceability.
* Reviewer validation.
* Re-extraction.
* Document comparison.
* Audit reporting.
* Detection of altered or missing source content.

---

# 6. Rendering Requirements

The system shall generate:

* PDF.
* HTML.
* DOCX.
* SVG.
* PlantUML source where applicable.
* Graphviz source where applicable.
* Machine-readable JSON.
* Machine-readable XML where required.
* Requirement matrices.
* Interface tables.
* Change reports.

Rendering shall be deterministic.

The same canonical source, renderer version, fonts, and configuration shall produce the same output.

---

# 7. Visual Fidelity Requirements

The system shall compare the regenerated document against the original.

Comparison methods shall include:

* Page count comparison.
* Text comparison.
* Bounding-box comparison.
* Line-position comparison.
* Table-grid comparison.
* Image-region comparison.
* Structural similarity.
* Edge comparison.
* Page-break comparison.
* Missing-element detection.

Example thresholds:

```yaml
visual_acceptance:
  page_count_difference: 0
  missing_text_blocks: 0
  semantic_text_difference: 0
  mean_text_position_error_pt: 1.5
  maximum_text_position_error_pt: 4.0
  mean_table_line_error_pt: 1.0
  minimum_structural_similarity: 0.95
```

Exact replication shall be defined by configurable tolerances rather than raw pixel identity.

---

# 8. Semantic Validation Requirements

The system shall validate that:

* Every requirement ID is unique.
* Every interface ID is unique.
* Every referenced requirement exists.
* Every referenced interface exists.
* Every figure reference resolves.
* Every table reference resolves.
* Every acronym has a definition where required.
* Every numeric engineering value has an appropriate unit.
* Every signal has a direction.
* Every message field has a defined length.
* Message fields do not overlap.
* Bit offsets are valid.
* Packet lengths match field definitions.
* Verification methods use allowed values.
* TBD and TBR items have status metadata.
* Deleted entities are represented in revision history.
* Changed requirements contain change records.

---

# 9. Human Review Requirements

The pipeline shall include a review interface.

Reviewers shall be able to:

* View the original page.
* View extracted text.
* View detected bounding boxes.
* Correct reading order.
* Correct OCR values.
* Correct tables.
* Correct row and column spans.
* Correct requirement classifications.
* Correct diagram relationships.
* Approve or reject extracted entities.
* View extraction confidence.
* Compare revisions.
* Regenerate affected pages.
* Record reviewer identity and timestamp.

No low-confidence engineering value shall become approved canonical data without review.

# 11. OpenSearch Decision

## 11.1 Is OpenSearch Required?

OpenSearch is not required for the initial extraction and regeneration pipeline.

The core system can operate with:

* Git.
* PostgreSQL.
* Object storage.
* FastAPI.
* Canonical YAML or JSON.
* Document generation tools.

OpenSearch should be added when the project requires advanced search, document discovery, semantic retrieval, or cross-document analysis.

---

## 11.2 What OpenSearch Would Provide

OpenSearch is useful for:

* Full-text search across many ICDs.
* Requirement lookup.
* Acronym lookup.
* Interface lookup.
* Searching table rows.
* Filtering by document, revision, subsystem, provider, or consumer.
* Finding all references to a signal or interface.
* Hybrid keyword and vector search.
* Retrieval-augmented generation.
* Cross-document traceability.
* Revision comparison support.
* Finding related requirements.
* Identifying duplicated or conflicting language.

Example queries:

```text
Find every requirement that references IF-CMD-001.

Find every document that specifies a 28 V interface.

Find all signal definitions using units of milliseconds.

Find all requirements changed between revisions B and C.

Find all references to a named spacecraft subsystem.

Find requirements similar to REQ-CMD-001.

Find every table row containing a CCSDS packet identifier.
```

---

## 11.3 What OpenSearch Should Not Do

OpenSearch shall not be:

* The authoritative data store.
* The primary editing interface.
* The canonical document model.
* The repository for approved requirements.
* The source used directly to regenerate official documents.
* The only location containing embeddings or extracted entities.

OpenSearch data shall always be rebuildable from the canonical source.

Correct architecture:

```text
Canonical YAML or JSON
    ↓
Validation
    ↓
PostgreSQL and Git records
    ↓
OpenSearch indexing
```

Incorrect architecture:

```text
OpenSearch
    ↓
Official ICD generation
```

---

## 11.5 Search Modes

OpenSearch may support:

### Keyword Search

Use BM25 for:

* Exact terminology.
* Identifiers.
* Requirement wording.
* Acronyms.
* Protocol names.
* Units.

### Metadata Filtering

Filter by:

* Document.
* Revision.
* Section.
* Interface.
* Requirement type.
* Verification method.
* Review status.
* Confidence.
* Provider.
* Consumer.
* Date.

### Vector Search

Use vector search for:

* Similar requirement discovery.
* Related interface discovery.
* Semantic questions.
* RAG.
* Duplicate-language detection.
* Contradiction candidate discovery.

### Hybrid Search

Recommended query model:

```text
BM25 keyword score
    +
vector similarity score
    +
metadata filters
    +
relationship expansion
```

---

## 11.6 When to Add OpenSearch

Add OpenSearch during the first release when:

* Hundreds or thousands of documents will be processed.
* Users need cross-document search.
* RAG is a primary requirement.
* Requirements must be searched semantically.
* Search latency matters.
* A requirement discovery portal is needed.
* The system will compare many revisions.
* The system will support organisation-wide retrieval.

Delay OpenSearch when:

* The initial goal is converting one or several PDFs.
* The primary goal is document reconstruction.
* Search can be handled by PostgreSQL.
* There is not yet a stable canonical schema.
* The indexing model is likely to change rapidly.
* Operational complexity must remain low.

---

## 11.7 Initial Recommendation

OpenSearch should be considered but should not block the initial implementation.

Recommended delivery sequence:

```text
Phase 1
    PDF ingestion
    Extraction
    Canonical schema
    Human review
    PDF regeneration
    Validation

Phase 2
    Revision management
    Cross-reference validation
    Improved diagram extraction
    Improved table extraction

Phase 3
    OpenSearch
    Hybrid search
    Embeddings
    RAG
    Cross-document analytics
```

If search and RAG are central project requirements from the beginning, OpenSearch may be introduced during Phase 1 as a derived index.

# 12. Bedrock Model Applicability

Amazon Bedrock models may assist with:

* Document-block classification.
* Requirement classification.
* Table-column interpretation.
* Acronym expansion.
* Entity linking.
* Diagram interpretation.
* Candidate PlantUML generation.
* Candidate SVG structure generation.
* Cross-reference detection.
* Contradiction identification.
* Revision summaries.
* Natural-language search.
* RAG responses.

Bedrock models shall not autonomously:

* Change normative requirement text.
* Invent units.
* Infer unsupported bit offsets.
* Infer signal direction without evidence.
* Replace low-confidence numbers.
* Approve extracted requirements.
* Generate official output without deterministic validation.

All model output shall:

* Use structured JSON responses.
* Validate against JSON Schema.
* Include confidence.
* Include source references.
* Be reviewable.
* Be reproducible where practical.
* Retain model name and model version metadata.

# 17. Principal Risks

## PDF Ambiguity

PDF stores visual placement rather than complete logical document meaning.

Mitigation:

* Use multiple extractors.
* Preserve geometry.
* Preserve source regions.
* Require human review.

## Table Complexity

Merged cells and multi-page tables may be reconstructed incorrectly.

Mitigation:

* Use an extraction ensemble.
* Retain grid geometry.
* Add a correction interface.
* Validate row and column consistency.

## Diagram Ambiguity

Arrows, labels, and relationships may be visually unclear.

Mitigation:

* Preserve original figure.
* Use vector extraction where possible.
* Use vision models only as assistants.
* Require human approval.

## Model Hallucination

A language or vision model may invent technical details.

Mitigation:

* Require structured output.
* Validate every output.
* Preserve verbatim text.
* Reject unsupported values.
* Maintain evidence links.

## Visual Differences

Fonts, antialiasing, and pagination may prevent exact pixel matches.

Mitigation:

* Use controlled fonts and renderer versions.
* Compare geometry and semantics in addition to pixels.
* Define tolerances.
* Preserve original page dimensions.

## Schema Instability

The ICD schema may evolve as more documents are processed.

Mitigation:

* Version schemas.
* Add migration tools.
* Keep raw extraction records.
* Avoid premature OpenSearch coupling.

# 18. Acceptance Criteria

The initial system will be considered successful when it can:

1. Ingest a representative NASA ICD PDF.
2. Classify every page.
3. Extract native text with coordinates.
4. OCR scanned pages.
5. Reconstruct the section hierarchy.
6. Detect candidate requirements.
7. Extract representative tables.
8. Preserve figures and source geometry.
9. Store the result in schema-validated YAML or JSON.
10. Allow a reviewer to correct extracted content.
11. Regenerate a readable PDF.
12. Preserve all approved requirement text.
13. Trace every generated requirement back to its original page.
14. Produce semantic validation results.
15. Produce visual comparison results.
16. Rebuild all derived outputs from the canonical source.
17. Add OpenSearch later without changing the canonical data model.

# 19. Final Architecture Recommendation

The recommended architecture is:

```text
Canonical source
    YAML or JSON

Validation
    Pydantic and JSON Schema

Physical document model
    Layout blocks, geometry, fonts, tables, and provenance

Engineering model
    Requirements, interfaces, signals, messages, and relationships

Exact editable graphics
    SVG

Semantic diagrams
    PlantUML and Graphviz

Plots
    Matplotlib

Document rendering
    Jinja2, HTML, CSS, and WeasyPrint

Storage
    Git, PostgreSQL, and S3 or MinIO

Review
    React, PDF.js, and SVG editing

Intelligence
    Optional Amazon Bedrock models

Search
    Optional derived OpenSearch indexes
```

OpenSearch should be included in the architecture as an optional search and analysis layer.

It should not be required for the initial PDF-to-ICD conversion capability, and it should never become the authoritative document repository.
